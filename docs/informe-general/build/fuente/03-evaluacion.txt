# 3. Evaluación de Seguridad
La evaluación sigue la separación de enfoques de NIST SP 800-115 (Scarfone et al., 2008). La caja negra no usa ningún conocimiento del código. La caja gris dirige las cargas útiles con el conocimiento de rutas y modelos. La caja blanca revisa el código fuente. Los resultados de cada enfoque se presentan por separado, para no atribuir a una prueba de caja negra lo que se descubrió leyendo el código. Cada batería se ejecutó primero contra el laboratorio vulnerable, para obtener el riesgo inherente, y después contra la variante corregida, la imagen cloud en local y el despliegue real de Render.
## 3.1 Pentesting Caja Negra
### Superficie de ataque y perímetro
La superficie expuesta se enumeró de forma reproducible desde `app/server.ts`. Comprende 109 rutas declaradas con ruta literal (50 GET, 40 POST, 13 PUT, 5 DELETE y 1 PATCH), unas 81 rutas bajo `/rest`, `/api` y `/b2b`, y 14 modelos expuestos como API CRUD automática. Incluye además tres puntos de entrada de archivos (`/file-upload`, `/profile/image/url` y `/rest/memories`), rutas estáticas con listado (`/ftp`, `/encryptionkeys`, `/support/logs`) y un endpoint de métricas sin autenticación (`/metrics`). Juice Shop no tiene webhooks entrantes ni salientes. La {T:perimetro} delimita los puertos y endpoints de cada entorno.

### Caja blanca
La revisión de código combinó Semgrep, CodeQL y lectura manual (apartado 3.5). Su hallazgo más grave es la clave privada RS256 codificada en `lib/insecurity.ts` (CWE-798). Con ella cualquiera que lea el código público puede forjar sesiones de cualquier usuario sin explotar ninguna inyección. No se automatizó el forjado ni se versionó la clave. La caja blanca también ubicó las consultas SQL construidas con plantillas de texto (`routes/login.ts:34`, `routes/search.ts:23`), el uso de `eval` y `vm` sobre datos del usuario, el hash MD5 sin sal y la API automática sin verificación de propietario. Esta revisión orientó los parches del apartado 4.3.

## 3.4 Evaluación de Plugins y Themes
### Aplicabilidad
Juice Shop no tiene un sistema de plugins ni de temas como el de los CMS tradicionales. El título se conserva por la estructura obligatoria, y su contenido se aplica a los dos elementos equivalentes que sí existen. El primero son los componentes de terceros que extienden la aplicación: 2745 componentes en el SBOM de la imagen oficial, generado con Syft en formato CycloneDX (Ecma International, 2024). El segundo es la capa de presentación, el frontend Angular, que cumple el papel del tema. No se afirma la existencia de plugins o temas tradicionales.
### Componentes de terceros
Los componentes se evaluaron con npm audit, OSV-Scanner y Grype (apartado 3.6). Destacan bibliotecas directas desactualizadas con impacto en seguridad: `jsonwebtoken` 0.1.0 y 0.4.0, `express-jwt` 0.1.3, `sanitize-html` 1.4.2, `marsdb` 0.6.11, y `lodash` 2.4.2 y `crypto-js` 3.3.0 como dependencias transitivas. Además, el código incluye material didáctico de los retos (`data/static/codefixes/`) que el SAST marca como inyecciones, aunque no se ejecuta. Se documentó como excepción y no se ocultó.
### Frontend y XSS en navegador
El frontend se evaluó con una prueba de XSS en un navegador real. Con Chromium (Playwright 1.49.1) se cargó la carga útil `<iframe src="javascript:alert(...)">` en seis vectores: DOM en la búsqueda, reflejado en el seguimiento de pedidos, y almacenado en opiniones, productos, correo del usuario visto por el administrador y última IP de inicio de sesión. Una ejecución cuenta cuando aparece el diálogo o el iframe en el DOM. La {T:xss} resume los resultados.

## 3.7 Evaluación de Contenedores y Kubernetes
### Aplicabilidad de Kubernetes
El proyecto no usa Kubernetes. La orquestación local se hace con Docker Compose y el despliegue cloud es un servicio de contenedor gestionado por Render. Por ello no se presentan resultados de herramientas específicas de Kubernetes. Los principios aplicables de NIST SP 800-190 se evalúan sobre las imágenes y el entorno de ejecución de los contenedores realmente usados (Souppaya et al., 2017): imágenes mínimas y fijadas, escaneo de vulnerabilidades, usuario no root, sistema de archivos de solo lectura, capacidades mínimas, límites de recursos y separación de redes.
